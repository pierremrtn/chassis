## Core Concepts

A Chassis application is wired bottom-up at startup: repositories construct first (no dependencies), the Mediator is constructed from those repositories, and the widget tree consumes the Mediator through `ViewModelProvider`s that build ViewModels on demand. This unidirectional dependency graph is the same shape Chassis enforces throughout — UI depends on ViewModels, ViewModels depend on the Mediator, the Mediator depends on repositories, repositories depend on infrastructure.

> The dependency tree flows naturally — repositories have no dependencies, the Mediator depends on repositories, ViewModels depend on the Mediator, and widgets depend on ViewModels.
> — `docs/coding_rules.md`

The Mediator referenced everywhere is `AppMediator`, generated by `chassis_builder` from the `@ChassisApp()` annotation on the composition-root library. Its constructor requires every deduplicated dependency of every `@chassisHandler`-annotated handler as a required named parameter — adding a handler that depends on a new repository makes the constructor require that repository, a compile error until the composition root provides it. This is the framework's way of preventing wiring drift. See `chassis-register-handler-with-codegen` for the handler-side workflow.

No `build.yaml` is needed: `chassis_builder` applies automatically to any package that lists it as a dev dependency (`auto_apply: dependents`).

## The Dependency Tree

```
┌─────────────────────────────────────┐
│ Widget (StatelessWidget / Stateful) │  reads context.select((TViewModel vm) => ...)
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ ViewModel<State, Event>             │  depends on AppMediator (or a module interface)
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ AppMediator (generated)             │  constructor requires every handler dependency
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ Repository implementations         │  depend on infrastructure (Firebase, REST)
└─────────────────────────────────────┘
```

Each layer depends only on the layer immediately below, through an interface. The composition root is the place this graph actually gets built — typically a small `initializeDependencies()` function called once at app startup, before `runApp()`.

## The Composition Root: `@ChassisApp`

The composition root is a library whose library directive is annotated with `@ChassisApp()`. The generator emits the concrete mediator in `<file>.chassis.dart`, next to the annotated file:

```dart
// lib/app/app.dart
@ChassisApp(mediatorName: 'AppMediator')
library;

import 'package:chassis/chassis.dart';
import 'package:my_app/features/features.dart'; // barrel reaching every handler
// generates lib/app/app.chassis.dart: class AppMediator extends Mediator { ... }
```

Three properties of the generated class matter at the composition root:

1. **The constructor requires every handler dependency** as a required named parameter (deduplicated across handlers). The parameter name is the dependency's type name, decapitalized — `TodoRepository` becomes `todoRepository:`. The constructor body instantiates each handler and registers it.
2. **Every generated method dispatches through `run` / `read` / `watch`**, so middlewares always apply. `mediator.addMiddleware(LoggingMiddleware())` observes every typed call.
3. **Handler discovery follows the import graph.** Only `@chassisHandler` classes reachable from the annotated library (within the app's own package), plus the handlers of each listed module, are registered. The composition-root file must import the application layer — a feature barrel keeps this to one line.

Modules composed from shared packages are listed in the annotation: `@ChassisApp(modules: [AuthModule])` makes the generated class `implements AuthMediator`, so a missing handler is a compile error, never a runtime surprise. See `chassis-organize-feature` for the module story.

## Where the Mediator Lives

The prescribed pattern is to declare the `AppMediator` as a top-level (`late final`) reference initialized in `initializeDependencies()`:

```dart
late final AppMediator mediator;

void initializeDependencies() {
  final todoRepository = InMemoryTodoRepository();
  mediator = AppMediator(todoRepository: todoRepository)
    ..addMiddleware(LoggingMiddleware());
}
```

> Declare the Mediator as a global variable so it can be accessed from anywhere in the route declarations without threading it through constructor parameters.
> — `docs/coding_rules.md`

The alternative — passing the Mediator down the widget tree as a parameter — quickly becomes unwieldy because every route declaration needs it. A top-level reference initialized once at startup is the convention. Tests bypass it by constructing an `AppMediator` (with mock repositories) directly in `setUp`.

## Rules

- **DO** annotate the library directive of one file with `@ChassisApp()` — a file that (transitively) imports every handler of the app — and list shared modules in `modules:`. *Handler discovery walks the import graph from the annotated library; an unreachable handler is silently absent from the generated mediator.*
- **DO** declare `late final AppMediator mediator;` at the top level of `main.dart` (or a dedicated `app/composition_root.dart`) and initialize it in a single `initializeDependencies()` function called once before `runApp()`.
- **DO** construct repository implementations first, then pass them to `AppMediator(...)` as named arguments. *The generated constructor requires every dependency injected by every reachable handler; the parameter name is the dependency's type name, decapitalized.*
- **DO** install `LoggingMiddleware` by default with `..addMiddleware(LoggingMiddleware())`. *Every dispatch is then traced — request, params, elapsed time, and errors with stack traces. Middlewares apply to every generated method because each one dispatches through `run`/`read`/`watch`.*
- **DO** use `ViewModelProvider<TViewModel>(create: (_) => TViewModel(mediator), child: ...)` (or `ViewModelProvider.withEventListener` for event-driven screens) at each route or screen boundary. *The provider owns the ViewModel's lifecycle.*
- **DO** keep `initializeDependencies()` focused on construction. Long-running work (fetching remote config, opening a database) belongs in async setup that runs *before* `runApp()` if it must complete first, or inside a repository constructor / first call if it can be lazy.
- **DO** depend on repository **interfaces** (`TodoRepository`, `UserRepository`) in handlers so the generated constructor parameters are interface-typed. *Interfaces let tests substitute mocks and let production swap implementations without touching the composition root structure.*
- **CONSIDER** running `WidgetsFlutterBinding.ensureInitialized()` before any platform-channel call (database open, local storage access) in `initializeDependencies()`.
- **CONSIDER** an `app/composition_root.dart` file for non-trivial applications, separate from `main.dart`. Keeps `main.dart` to `void main() { initializeDependencies(); runApp(MyApp()); }`.
- **DON'T** write a `build.yaml`. *`chassis_builder` applies automatically to any package that depends on it as a dev dependency; a stale `build.yaml` referencing pre-1.0 builders breaks the build.*
- **DON'T** instantiate handlers manually and call `mediator.registerCommandHandler(...)` alongside the generated `AppMediator`. *The generated constructor already registers every reachable handler; a duplicate registration throws `DuplicateHandlerException` at startup.*
- **DON'T** thread the Mediator through widget constructors as a parameter. *Use the top-level reference; ViewModelProviders read it where they construct VMs.*
- **DON'T** create the Mediator inside a widget's `build()` or in a `ViewModelProvider.create:` callback. *The Mediator is application-scoped, not screen-scoped — building it per route would re-register handlers, invalidate caches inside repositories, and silently break shared state.*

## Workflow

- [ ] **Step 1 — Add dependencies** to `pubspec.yaml`: `chassis: ^1.0.0` and `chassis_flutter: ^1.0.0` (which re-exports `provider`), plus `chassis_builder: ^1.0.0` and `build_runner: ^2.15.0` in `dev_dependencies`. No `build.yaml`.
- [ ] **Step 2 — Define repository interfaces** in `lib/<feature>/domain/<resource>_repository.dart`. Handlers depend on these interface types, so the generated constructor will require them.
- [ ] **Step 3 — Implement the repositories** under `lib/<feature>/infrastructure/<provider>_<resource>_repository.dart`. This is where infrastructure exception mapping lives — see `chassis-handle-errors`.
- [ ] **Step 4 — Author handlers and ViewModels** following `chassis-create-command`, `chassis-create-read-query`, `chassis-create-watch-query`, and `chassis-create-view-model`. Annotate handlers with `@chassisHandler`.
- [ ] **Step 5 — Declare the composition root.** `@ChassisApp()` (plus `modules: [...]` if the app composes shared packages) on the library directive of a file that imports the application layer.
- [ ] **Step 6 — Generate `AppMediator`** by running `dart run build_runner build --delete-conflicting-outputs`. The output is `<file>.chassis.dart` next to the annotated file.
- [ ] **Step 7 — Write the wiring.** Declare `late final AppMediator mediator;`. Implement `initializeDependencies()` that constructs each repository, assigns `mediator = AppMediator(...)` with the repositories as named arguments, and installs `LoggingMiddleware` (plus crash reporting if any — see `chassis-handle-errors`).
- [ ] **Step 8 — Compose the root widget tree.** `runApp(MaterialApp(home: ViewModelProvider<TViewModel>(create: (_) => TViewModel(mediator), child: ...)))`. Use `ViewModelProvider.withEventListener` when the screen handles events. See `chassis-consume-view-model` and `chassis-handle-view-model-events`.

## Examples

### `pubspec.yaml`

```yaml
dependencies:
  flutter:
    sdk: flutter
  chassis: ^1.0.0
  chassis_flutter: ^1.0.0

dev_dependencies:
  flutter_test:
    sdk: flutter
  chassis_builder: ^1.0.0
  build_runner: ^2.15.0
```

### Minimal composition root and `main.dart` for a single-screen app

```dart
// lib/app/app.dart
@ChassisApp(mediatorName: 'AppMediator')
library;

import 'package:chassis/chassis.dart';
import 'package:my_app/features/todos/todos.dart'; // barrel reaching every handler
```

```dart
// lib/main.dart
import 'package:flutter/material.dart';
import 'package:chassis_flutter/chassis_flutter.dart';

import 'app/app.chassis.dart'; // generated
import 'features/todos/infrastructure/in_memory_todo_repository.dart';
import 'features/todos/presentation/todo_screen.dart';
import 'features/todos/presentation/todo_view_model.dart';
import 'features/todos/presentation/todo_event.dart';

late final AppMediator mediator;

void initializeDependencies() {
  final todoRepository = InMemoryTodoRepository();
  mediator = AppMediator(todoRepository: todoRepository)
    ..addMiddleware(LoggingMiddleware());
}

void main() {
  initializeDependencies();
  runApp(const TodoApp());
}

class TodoApp extends StatelessWidget {
  const TodoApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Todos',
      home: ViewModelProvider.withEventListener<TodoViewModel, TodoEvent>(
        create: (_) => TodoViewModel(mediator),
        onEvent: (context, _, event) {
          if (event case TodoAddedEvent()) {
            ScaffoldMessenger.of(context).showSnackBar(
              const SnackBar(content: Text('Todo added')),
            );
          }
        },
        child: const TodoScreen(),
      ),
    );
  }
}
```

### Larger app with a module, several repositories, and middlewares

```dart
// lib/app/app.dart
@ChassisApp(modules: [AuthModule], mediatorName: 'AppMediator')
library;

import 'package:auth/auth.dart'; // shared module package
import 'package:chassis/chassis.dart';
import 'package:my_app/features/features.dart';
// generates: class AppMediator extends Mediator implements AuthMediator
```

```dart
// lib/main.dart
import 'package:chassis/chassis.dart';
import 'package:flutter/material.dart';
import 'package:chassis_flutter/chassis_flutter.dart';

import 'app/app.chassis.dart'; // generated
import 'features/auth/infrastructure/firebase_auth_repository.dart';
import 'features/users/infrastructure/firestore_user_repository.dart';
import 'features/orders/infrastructure/firestore_order_repository.dart';
import 'infrastructure/crash_reporting/sentry_crash_reporter.dart';
import 'infrastructure/crash_reporting/crash_reporting_middleware.dart';
import 'router.dart';

late final AppMediator mediator;

Future<void> initializeDependencies() async {
  WidgetsFlutterBinding.ensureInitialized();

  final crashReporter = SentryCrashReporter();
  await crashReporter.init();

  mediator = AppMediator(
    authRepository: FirebaseAuthRepository(),
    userRepository: FirestoreUserRepository(),
    orderRepository: FirestoreOrderRepository(),
  )
    ..addMiddleware(LoggingMiddleware())
    ..addMiddleware(CrashReportingMiddleware(crashReporter));
}

Future<void> main() async {
  await initializeDependencies();
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp.router(
      title: 'Shop',
      routerConfig: appRouter, // routes use the top-level `mediator`
    );
  }
}
```

Each route in `appRouter` wraps its screen in a `ViewModelProvider` that reads the top-level `mediator`. The composition root constructs the graph once; widgets never see the Mediator construction code.

### Per-route ViewModel provision

```dart
GoRoute(
  path: '/profile/:userId',
  builder: (context, state) {
    final userId = state.pathParameters['userId']!;
    return ViewModelProvider.withEventListener<UserProfileViewModel, UserProfileEvent>(
      create: (_) => UserProfileViewModel(mediator, userId: userId),
      onEvent: (context, _, event) { /* ... */ },
      child: const UserProfileScreen(),
    );
  },
);
```

The route owns the ViewModel's lifecycle: when the user navigates away the provider disposes, which disposes the VM, which cancels its `watch(...)` subscriptions automatically.

### Anti-pattern: manual handler registration

```dart
// ❌ Manual wiring loses the compile-time guarantee that every annotated
// handler is registered with its dependencies.
class ManualMediator extends Mediator {
  ManualMediator(TodoRepository repo) {
    registerQueryHandler(WatchTodosHandler(repository: repo));
    registerCommandHandler(AddTodoHandler(repository: repo));
    registerCommandHandler(ToggleTodoHandler(repository: repo));
  }
}
```

```dart
// ✅ Use the generated AppMediator. Adding a handler with @chassisHandler
// updates the constructor automatically; missing dependencies become
// compile errors at the composition root.
mediator = AppMediator(todoRepository: todoRepository)
  ..addMiddleware(LoggingMiddleware());
```

### Anti-pattern: building the Mediator inside a widget

```dart
// ❌ Re-creates the Mediator on every rebuild. Repositories that hold caches
// or stream controllers will be re-instantiated, silently breaking shared state.
class TodoRoute extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    final mediator = AppMediator(todoRepository: InMemoryTodoRepository());
    return ViewModelProvider<TodoViewModel>(
      create: (_) => TodoViewModel(mediator),
      child: const TodoScreen(),
    );
  }
}
```

```dart
// ✅ Build once at startup, use everywhere.
late final AppMediator mediator;
void initializeDependencies() {
  mediator = AppMediator(todoRepository: InMemoryTodoRepository())
    ..addMiddleware(LoggingMiddleware());
}
```
